# ADR-005: Timer-driven стейт-машина доставки

- Статус: accepted
- Дата: 2026-09-18
- Контекст PRD: FR-DELIVERY-01, продуктовое решение пользователя (простая стейт-машина по таймеру, без гео/карты)

## Контекст

Продуктовая цель — эффект предвкушения ("где мой курьер?") без реальной логистики. Пользователь явно выбрал вариант "простая стейт-машина по таймеру" вместо гео-симуляции с координатами на карте — это сознательное упрощение, снижающее сложность фронтенда (не нужна карта) при сохранении дофаминового эффекта через прогресс-бар/ETA.

## Решение

### Конечный автомат

```
assembling (10-30s) -> courier_assigned (instant) -> in_transit (60-180s) -> delivered (terminal)
                                                    \-> [10% chance] delivery_delayed (+15-45s) -> in_transit
```

- Длительности — случайные величины (uniform distribution в указанных диапазонах), генерируются при входе в состояние и детерминированно логируются (seed на order_id для воспроизводимости в тестах).
- `delivery_delayed` — намеренный элемент "прерывистого подкрепления" (variable reward), усиливающий дофаминовый эффект: пользователь не знает точно, будет ли задержка.

### Механизм таймера

Реализуется НЕ через `time.Sleep` в горутине (не переживает рестарт процесса), а через **таблицу отложенных задач** `delivery.scheduled_transitions` (order_id, target_status, fire_at, fired boolean) + фоновый `delivery-scheduler` (часть `cmd/worker`), который каждые 1с выбирает `fire_at <= now() AND fired = false FOR UPDATE SKIP LOCKED`, выполняет переход и планирует следующий.

Это даёт: устойчивость к рестарту сервиса (после падения scheduler продолжит с того же места), горизонтальную безопасность (SKIP LOCKED предотвращает дублирование при нескольких инстансах worker в будущем), и простую тестируемость (можно мокать `clock.Now()`).

### Публикация статусов

Каждый переход стейт-машины пишет outbox-событие `delivery.status_changed.v1` (ADR-003) → `notification` модуль транслирует его в SSE-поток, подписанный фронтендом на конкретный `order_id`.

## Альтернативы

| Вариант | Почему отклонён |
|---|---|
| Гео-симуляция с координатами и картой (пользователь явно отклонил) | Больше сложности фронтенда (карта, интерполяция маршрута) без пропорционального прироста дофаминового эффекта для этого продукта |
| `time.AfterFunc`/горутины в памяти | Не переживает рестарт процесса — потерянный таймер = зависший заказ, недопустимо |
| Cron-джоба раз в минуту вместо scheduler с секундной гранулярностью | Диапазоны длительности (10-30с) требуют более частого тика для точности UX |
| Хранение стейт-машины полностью в Kafka (event sourcing без Postgres-таблицы) | Избыточно для внутреннего таймера; Postgres проще для точечных `fire_at` запросов и не требует переигрывания топика для восстановления состояния |

## Последствия

- (+) Устойчиво к рестартам, просто тестируется, не требует геоданных/карт.
- (+) `delivery_delayed` как программируемый элемент неопределённости — сознательный продуктовый инструмент вовлечения.
- (-) Требует отдельного worker-процесса и таблицы планировщика — небольшой дополнительный компонент инфраструктуры.
- (-) При переходе на multi-instance worker в будущем нужен distributed lock (уже покрыт `FOR UPDATE SKIP LOCKED`).
