# ADR-004: Границы модулей и контракты между ними

- Статус: accepted
- Дата: 2026-09-18
- Контекст PRD: NFR-MAINT-01

## Контекст

ADR-001 постулирует модульный монолит, но без конкретики это декларация без исполнения. Особенно важно для agentic development (см. `AGENTS.md`): разные AI-агенты будут параллельно работать над разными модулями, и единственная защита от конфликтов и "протекания" абстракций — жёсткие, проверяемые линтером границы.

## Решение

### Слоистая структура внутри модуля

```
internal/modules/{name}/
├── domain/          # Сущности, value objects, доменные ошибки, бизнес-правила. Zero внешних зависимостей.
├── usecase/         # Оркестрация сценариев (application services). Зависит от domain + портов.
├── port/            # Интерфейсы, которые usecase ожидает от внешнего мира (repository, publisher, clock)
├── adapter/
│   ├── postgres/    # Реализация repository-портов через sqlc
│   ├── kafka/       # Producer/consumer адаптеры
│   └── httpapi/      # chi-роуты, DTO, маппинг domain <-> JSON
└── module.go        # Публичная фабрика модуля: New(deps) -> PublicAPI, единственная точка входа снаружи
```

### Правило видимости

- Единственный экспортируемый тип из модуля — реализация интерфейса, объявленного в `internal/contracts/{name}.go`.
- Пример: `internal/contracts/payment.go` объявляет `type Provider interface { Charge(ctx, OrderID, AmountRUB) (PaymentResult, error) }`. Модуль `order` импортирует ТОЛЬКО `internal/contracts`, никогда `internal/modules/payment/*`.
- Проверка соблюдения: `depguard` правило в `.golangci.yml`, запрещающее импорт `internal/modules/**` откуда-либо, кроме `cmd/**` (composition root) и самого модуля.

### Composition root

`cmd/server/main.go` — единственное место, где все модули инстанцируются и связываются (dependency injection руками, без DI-фреймворка — на масштабе проекта framework избыточен и снижает читаемость для ревьюеров).

### Общие (shared) пакеты

`internal/platform/*` — горизонтальная инфраструктура без бизнес-логики (db pool, kafka client wrapper, logger, config, middleware). Модули МОГУТ импортировать `platform/*`, но `platform/*` никогда не импортирует `modules/*`.

## Альтернативы

| Вариант | Почему отклонён |
|---|---|
| Полная Clean Architecture с DI-контейнером (wire/fx) | Дополнительная магия/codegen усложняет онбординг агентов и ревью; ручной composition root прозрачнее для демонстрации архитектурного мышления |
| Package-by-layer (единый `handlers/`, `services/`, `repositories/` на весь проект) | Неизбежно превращается в god-package при росте; не даёт естественных границ для параллельной работы агентов |
| Мягкие границы (соглашение в документации, без линтера) | Недостаточно для agentic development — агенты будут нарушать границы при отсутствии автоматической проверки |

## Последствия

- (+) Границы модулей проверяются в CI, а не полагаются на дисциплину.
- (+) Каждый Epic из `docs/epics/` мапится 1:1 на модуль → агенты работают в изолированных директориях, минимум merge-конфликтов.
- (+) Замена адаптера (например, MockProvider → YooKassaProvider) не трогает usecase/domain слои.
- (-) Больше boilerplate (интерфейсы, DTO-маппинг) по сравнению с "быстрым" монолитом — осознанная плата за поддерживаемость и demo-ценность.
