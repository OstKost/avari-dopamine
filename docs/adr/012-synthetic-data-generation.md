# ADR-012: Детерминированная генерация синтетических данных

- Статус: accepted
- Дата: 2026-09-18
- Контекст PRD: FR-CATALOG-01, FR-PICKUP-01. Продуктовое решение: каталог и курьеры — 100% синтетические.

## Контекст

Пользователь подтвердил: никаких внешних партнёрских API/фидов для товаров, пункты выдачи — не реальные адреса, а сгенерированные точки со смещением. Нужен воспроизводимый, детерминированный способ генерации, чтобы: (а) demo-окружение и тесты видели одинаковые данные, (б) не требовалось внешних сетевых вызовов при старте.

## Решение

### Каталог (`FR-CATALOG-01`)

- `cmd/seed` — отдельная CLI-команда (`go run ./cmd/seed catalog`), выполняется один раз при первом поднятии окружения (не при каждом старте сервера).
- Генерация через Go-библиотеку `go-faker/faker` + собственные шаблоны категорий (`internal/modules/catalog/adapter/seed/templates.go`): 10 категорий (например "Гаджеты-пустышки", "Странные носки", "Съедобная канцелярия" — с юмористическим уклоном, соответствующим интересам пользователя к юмористическому tech-контенту), 150-300 товаров.
- Детерминированность: `rand.New(rand.NewSource(42))` — фиксированный сид, коммитится как часть seed-скрипта (не runtime random) — воспроизводимо на любой машине/CI.
- Изображения — не генерируются нейросетью в реальном времени (дорого/нестабильно для CI), а через детерминированный placeholder-сервис (`picsum.photos/seed/{product_id}/400/400` или локально сгенерированные SVG-плейсхолдеры с цветом на основе хэша id) — реалистично выглядит, не требует хранения бинарников в репозитории.

### Пункты выдачи (`FR-PICKUP-01`)

- При выборе пользователем базовой точки (геолокация или город) backend генерирует 5-8 точек: случайный азимут `θ ~ Uniform(0, 360°)` и расстояние `d ~ Uniform(100, 500)` метров, точка вычисляется через прямую геодезическую задачу (destination point given distance and bearing, формула на сфере с радиусом Земли 6371км) — стандартная формула, не требует внешнего geocoding API.
- Название ПВЗ — шаблон `{тип} на {псевдоулица}` из заготовленного пула (`"Пункт выдачи №{N}"`, `"Шкафчик у {ориентир}"`) — юмористически обыгрывает то, что это не настоящий адрес (сознательный элемент "игровой", не пытающийся выдать себя за реальную логистику).
- Курьеры (`FR-DELIVERY-01`): при назначении генерируется случайное имя из пула (faker `Name()`) + рейтинг `Uniform(4.2, 5.0)` — чисто косметический элемент погружения, не персистентная сущность с историей (не нужен модуль "курьеры" как отдельный домен — это value object внутри агрегата `delivery`).

## Альтернативы

| Вариант | Почему отклонён |
|---|---|
| Реальный товарный фид (например, открытые API типа OpenFoodFacts) | Пользователь явно предпочёл полностью синтетический подход — минимизирует внешние зависимости, максимизирует фокус ревью на архитектуре, а не на ETL |
| Runtime-генерация изображений через image-модель на каждый товар | Дорого, медленно, нестабильно для CI/demo; не даёт архитектурной ценности, пропорциональной затратам |
| Случайный (не детерминированный) сид при каждом запуске seed | Ломает воспроизводимость демо и тестов — разные ревьюеры увидят разные каталоги |
| Отдельный домен/модуль "courier" с постоянными сущностями | Избыточно — курьер не имеет собственного жизненного цикла вне конкретной доставки, это value object, а не aggregate root |

## Последствия

- (+) Полностью офлайн-воспроизводимая среда — никаких внешних API-ключей для запуска core-функциональности.
- (+) Детерминированность упрощает snapshot-тесты и демо-скрипты ("у всех ревьюеров одинаковый каталог").
- (+) Лёгкий юмористический тон в названиях товаров/ПВЗ поддерживает продуктовую идею "лёгкости", соответствует интересам пользователя.
- (-) Каталог не отражает реальный рыночный ассортимент — не проблема, так как FR-CATALOG-01 явно не про реальную торговлю.
