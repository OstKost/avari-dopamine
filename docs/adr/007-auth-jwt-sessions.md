# ADR-007: JWT access + refresh с ротацией в Redis

- Статус: accepted
- Дата: 2026-09-18
- Контекст PRD: FR-AUTH-01, FR-AUTH-02, NFR-SEC-01, NFR-SEC-02

## Контекст

Next.js SSR фронтенд (ADR-009) должен на сервере (RSC) уметь проверить, авторизован ли пользователь, до рендера — то есть auth-состояние должно быть читаемо из cookie синхронно, без дополнительного round-trip на каждый SSR-рендер, но с возможностью инвалидации (logout, компрометация).

## Решение

- **Access token**: JWT (HS256 достаточно на данном масштабе; ключ — `AUTH_JWT_SECRET`), TTL 15 минут, хранится в `httpOnly, Secure, SameSite=Lax` cookie. Содержит `sub` (user_id), `exp`, `iat`. Next.js middleware читает и валидирует его на каждом запросе без похода в БД (self-contained).
- **Refresh token**: случайный opaque токен (256 бит), TTL 30 дней, хранится в Redis (`refresh:{token_hash} -> user_id, family_id`) + отдельная `httpOnly` cookie. При обновлении access-токена refresh **ротируется**: старый немедленно инвалидируется, выпускается новый с тем же `family_id`.
- **Reuse detection**: если приходит уже инвалидированный refresh-токен той же `family_id` — считаем это компрометацией, инвалидируем ВСЮ family (все сессии пользователя), требуем повторный логин. Реализуется через хранение недавно инвалидированных токенов с коротким TTL (72ч) в Redis.
- **Logout**: удаляет refresh-запись из Redis, очищает обе cookie.
- **Rate limiting** (NFR-SEC-02): `internal/platform/ratelimit` — token bucket в Redis, ключ `ratelimit:auth:{ip}`, 5 попыток/мин на `/auth/login` и `/auth/register`.

## Альтернативы

| Вариант | Почему отклонён |
|---|---|
| Только сессии в Redis (без JWT) | Требует похода в Redis на КАЖДЫЙ запрос, включая SSR middleware — лишняя латентность и связанность фронтенда с Redis напрямую |
| Только JWT без refresh/ротации (долгоживущий access token) | Невозможность быстро инвалидировать скомпрометированный токен — неприемлемо по NFR-SEC-01 |
| NextAuth.js / Auth.js как готовое решение | Скрывает механику от ревьюера портфолио; цель — показать понимание auth-потоков вручную на Go-backend, фронтенд — тонкий клиент |
| OAuth-only (Google/GitHub) без email+пароль | Продукт ориентирован на быстрый, анонимный-по-духу онбординг; email+пароль проще демонстрировать без внешних OAuth-провайдеров в CI |

## Последствия

- (+) SSR может проверить авторизацию без сетевого вызова (self-contained JWT).
- (+) Компрометация refresh-токена обнаруживается и купируется (reuse detection).
- (-) HS256 требует общего секрета между всеми инстансами `apps/api` — приемлемо при single-node (ADR-002); при масштабировании до multi-instance переходим на RS256 с распределяемым публичным ключом.
- (-) Revocation access-токена до истечения TTL невозможна без доп. чёрного списка — приемлемый риск на 15-минутном окне для данного масштаба.
