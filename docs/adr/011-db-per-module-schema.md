# ADR-011: Postgres — отдельная схема на модуль, единая БД

- Статус: accepted
- Дата: 2026-09-18
- Контекст PRD: NFR-MAINT-01, ADR-001, ADR-002

## Контекст

ADR-001 требует изоляции данных модулей, но ADR-002 фиксирует single-node Postgres. Полное разделение на отдельные физические БД на 100 MAU избыточно (N connection pool'ов, N наборов миграций, сложнее делать consistent бэкап), но логическая изоляция всё равно нужна, чтобы предотвратить "чтение чужих таблиц напрямую SQL-запросом" как способ обойти границы модулей (ADR-004).

## Решение

- Одна физическая база `dopamine_market`, отдельная **Postgres-схема на модуль**: `identity`, `catalog`, `pickup`, `cart` (не используется — см. ADR-008), `order`, `payment`, `delivery`.
- Каждый модуль подключается со своим `search_path`, ограниченным своей схемой + `public` (для расширений типа `pgcrypto`/`uuid-ossp`).
- Миграции — раздельные наборы файлов на модуль (`apps/api/migrations/{module}/NNN_description.sql`), применяются через `goose` с namespace per схему, что позволяет агентам добавлять миграции своего модуля без конфликтов номеров с другими модулями.
- Межмодульные "внешние ключи" (например, `order_items.product_id` ссылается на товар из `catalog`) **не создаются как физический FK через схемы** — целостность обеспечивается на уровне usecase (валидация существования при записи), потому что физический cross-schema FK создаёт скрытую связанность, противоречащую ADR-004. Ссылка хранится как обычный UUID + денормализованный снапшот нужных полей (например, `order_items` хранит `product_name_snapshot`, `price_snapshot` — что также требуется бизнес-правилом "заказ хранит цену на момент покупки").

## Альтернативы

| Вариант | Почему отклонён |
|---|---|
| Общая схема `public` для всех таблиц | Не даёт даже логической изоляции — легко случайно писать JOIN между "чужими" таблицами, размывая границы модулей |
| Физически отдельные БД/инстансы Postgres на модуль | Оверинжиниринг на 100 MAU: N connection pool'ов, N бэкапов, сложные cross-schema аналитические запросы становятся невозможны без ETL |
| Cross-schema физические Foreign Keys | Создаёт неявную связанность на уровне схемы БД, которую агент может нарушить миграцией в одном модуле, сломав другой — противоречит принципу изолированной эволюции модулей |

## Последствия

- (+) Один Postgres-инстанс, один бэкап, одна connection pool конфигурация — просто для инфраструктуры данного масштаба.
- (+) `\dn` в psql сразу показывает границы модулей — наглядно для ревью.
- (+) Легко эволюционировать в отдельные БД позже (schema dump → restore в новую БД, минимальные изменения connection string).
- (-) Целостность ссылок между модулями — на уровне приложения, не БД — требует дисциплины в usecase-слое и явных тестов (Epic ORDER включает тест "создание заказа с несуществующим product_id отклоняется").
