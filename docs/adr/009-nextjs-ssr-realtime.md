# ADR-009: Next.js SSR + SSE для real-time статусов

- Статус: accepted
- Дата: 2026-09-18
- Контекст PRD: FR-NOTIF-01, продуктовый приоритет "Frontend SSR Next.js — прорабатывается глубже остального"

## Контекст

Фронтенд обозначен пользователем как один из трёх приоритетных фокусов портфолио (наравне с Go-архитектурой и agentic-процессом). Требуется показать актуальное владение Next.js App Router (RSC, SSR, стриминг), не просто SPA поверх API.

## Решение

### Рендеринг

- **Next.js 15, App Router.** Каталог (`/catalog`, `/product/[id]`) — Server Components с прямым fetch к Go API на сервере (без клиентского waterfall), кэшируется через Next.js `fetch` cache с ревалидацией по тегам (`revalidateTag('catalog')` при обновлении товара — на MVP каталог статичен, задел на будущее).
- **История заказов** (`/orders`) — Server Component с курсорной пагинацией, initial data приходит с сервера, дальнейшая пагинация — Server Actions.
- **Страница активного заказа** (`/orders/[id]`) — гибрид: начальный статус рендерится на сервере (SSR, без "мигания" пустого состояния), дальнейшие обновления — клиентский компонент, подписанный на SSE.
- **Корзина/чекаут** — Client Component (высокая интерактивность, оптимистичные обновления через `useOptimistic`).

### Real-time доставка статусов

- **Server-Sent Events**, не WebSocket: канал строго однонаправленный (server → client), что покрывает 100% потребности (обновления статуса заказа). SSE проще в реализации на Go (`http.Flusher`), не требует доп. библиотек, легче проходит через стандартные reverse-proxy/CDN настройки, автоматически переподключается браузером из коробки (`EventSource`).
- Эндпоинт `GET /api/orders/{id}/events` (module `notification`), держит соединение открытым, на новое сообщение из Kafka-consumer пишет `data: {...}\n\n`. При подключении сразу отправляет текущий снимок статуса (event `snapshot`), затем последующие diff-события (event `status_changed`) — покрывает FR-NOTIF-01 "переподключение восстанавливает текущий статус".
- Next.js клиентский компонент оборачивает `EventSource` в кастомный hook `useOrderStatus(orderId)`, обновляет локальное состояние (React state), драйвит анимацию прогресс-бара.

### Обмен типами API

`apps/api` генерирует OpenAPI-спеку (через `swaggo` аннотации или ручной `openapi.yaml`, см. Epic API-CONTRACT) → `apps/web` генерирует TypeScript-типы (`openapi-typescript`) — единый источник истины для контрактов, без ручной дублирующей типизации.

## Альтернативы

| Вариант | Почему отклонён |
|---|---|
| WebSocket вместо SSE | Двунаправленный канал не нужен (клиент никогда не отправляет данные через этот канал); WebSocket требует больше инфраструктурной возни (sticky sessions при масштабировании, отдельный upgrade-handshake) без пользы для этого use case |
| Polling (клиент опрашивает статус раз в N секунд) | Хуже UX (задержка до N секунд), больше нагрузки на backend при 100+ одновременных активных заказов; не демонстрирует real-time компетенцию |
| Pages Router (старый Next.js) | App Router — актуальный стандарт с 2024+, обязателен для демонстрации современного владения фреймворком |
| GraphQL + subscriptions | Избыточная сложность (отдельный GraphQL-слой) без пропорциональной пользы против REST+SSE для этого масштаба API |

## Последствия

- (+) SSR даёт быстрый first paint каталога/заказов, полностью соответствует Next.js best practices 2025+.
- (+) SSE — простая, надёжная, соответствующая задаче технология без лишней инфраструктуры.
- (+) Единый источник контрактов (OpenAPI) исключает дрейф типов между Go и TypeScript.
- (-) SSE-соединения держат открытые HTTP-коннекшены на backend — при 100 MAU с несколькими активными заказами одновременно (пик 10) это тривиально дешево; при росте потребует явного лимита на конкурентные SSE-соединения per instance (задокументировано как триггер пересмотра).
