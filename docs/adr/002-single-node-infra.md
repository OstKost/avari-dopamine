# ADR-002: Single-node инфраструктура для 100 MAU

- Статус: accepted
- Дата: 2026-09-18
- Контекст PRD: NFR-COST-01, scale_assumptions

## Контекст

Целевая нагрузка (100 MAU, ~200 заказов/день, пик 20 RPS) на 3-4 порядка меньше, чем требует HA-кластер Kafka/Postgres/Redis. При этом проект должен ДЕМОНСТРИРОВАТЬ полный стек (Kafka, Redis, Graylog, Postgres) — то есть отказ от инструментов не вариант, вопрос в топологии их развёртывания.

## Решение

Всё поднимается через один `docker-compose.yml` на одной VPS:

- **PostgreSQL**: один инстанс, без реплик. Ежедневный `pg_dump` в качестве бэкапа (cron внутри контейнера или systemd таймер на хосте).
- **Kafka**: single-broker в режиме KRaft (без Zookeeper) — актуальная схема для Kafka с 2024+, снижает число контейнеров и сложность.
- **Redis**: один инстанс, `appendonly yes` для персистентности корзин/сессий между рестартами.
- **Graylog**: один инстанс + встроенный Elasticsearch/OpenSearch + MongoDB (это стандартный минимальный стек Graylog, тройка контейнеров неизбежна).
- Все контейнеры — в одной Docker-сети `dopamine-net`, без внешних облачных managed-сервисов (сознательно, чтобы весь стек был воспроизводим локально одной командой).

Explicit non-goals на этом масштабе: Kubernetes, service mesh, read-replicas, Kafka-кластер из 3+ брокеров, Redis Sentinel/Cluster.

## Альтернативы

| Вариант | Почему отклонён |
|---|---|
| Managed Cloud (RDS, MSK, ElastiCache) | Стоимость неоправданна для портфолио-проекта; цель — показать умение самостоятельно поднять и настроить инфраструктуру (Docker/Linux — заявленная компетенция) |
| Kubernetes (k3s/minikube) | Ради 1 хоста и 100 MAU — чистый оверинжиниринг, усложняет demo-запуск для ревьюеров |
| Убрать Kafka/Graylog совсем, заменить на прямые вызовы и stdout-логи | Убивает главную цель портфолио — показать event-driven архитектуру и наблюдаемость |

## Последствия

- (+) Весь стек поднимается одной командой `docker compose up`, воспроизводим на ноутбуке ревьюера.
- (+) Явно задокументированный путь роста (см. секцию ниже) показывает, что упрощение — осознанное архитектурное решение, а не неспособность спроектировать HA.
- (-) Единая точка отказа на каждом слое — недопустимо для продакшна с реальными пользователями, но приемлемо и явно задокументировано для 100 MAU.
- (-) Нет автоматического failover — при падении Postgres нужен ручной restart контейнера (задача Epic OPS).

## Путь роста (документируется, не реализуется на MVP)

1. 100 → 1000 MAU: вертикальное масштабирование VPS, Postgres connection pooling (pgbouncer), Redis остаётся single-node.
2. 1000 → 10 000 MAU: Postgres read-replica для каталога/истории заказов, Kafka 3-broker кластер, горизонтальное масштабирование `apps/api` за балансировщиком (модули остаются в одном бинарнике — stateless, кроме delivery-таймеров, которые переезжают в Kafka-managed state, см. ADR-005).
3. > 10 000 MAU: рассмотреть вынос `delivery` и `notification` в отдельные сервисы (уже готовые контракты из ADR-001 упрощают это).
